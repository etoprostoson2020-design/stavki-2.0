# FOOTBALL STRATEGY LAB

Исследовательская лаборатория футбольных стратегий. **Не приложение для ставок.**
Ищет, проверяет и замораживает стратегии; подтверждённые уходят в отдельный
Decision App через versioned JSON contract.

Реализация архитектурного пакета v1 (документы 01–10).

> **Размещение.** По документу 08 Strategy Lab и Decision App — разные системы.
> Сейчас лаборатория лежит подкаталогом `strategy_lab/` внутри репозитория
> Decision App. Это временно; при первом же экспорте её нужно вынести
> в собственный репозиторий, чтобы контракт между системами был настоящим.

## Быстрый старт

```bash
cp .env.example .env          # секреты только здесь, в git не попадает
docker compose up -d          # postgres + redis + api + worker
make migrate                  # схема БД
make slice                    # первый vertical slice целиком
make test                     # тесты, включая Red Team
```

Без Docker (локальные postgres/redis):

```bash
export $(grep -v '^#' .env | xargs)
make migrate && make slice && make test
```

## Vertical slice

```
Football-Data CSV → RAW snapshot (sha256) → Data Audit → Canonical Fixtures
    → Time Machine (as_of) → Feature Factory → Experiment → result_hash
```

`make slice` печатает отчёт аудита, число канонических матчей, покрытие признаков
и результат эксперимента с хэшем. Повторный запуск обязан дать тот же хэш.

## Валидация (фаза 6)

```
Search Batch -> Null World (порог батча) -> Qualification Gate -> Robustness
    -> Freeze (формула + критерий) -> OOS -> PASS/WEAK_PASS/INCONCLUSIVE/FAIL
    -> KEEP/MUTATE/PARK/KILL
```

`make validate` прогоняет батч из 120 кандидатов и 40 негативных контролей,
считает порог FWER нулевыми мирами, проверяет лучшего кандидата на устойчивость,
замораживает его вместе с критерием и оценивает на блоке валидации.

Три вещи, которых в архитектурном пакете не было:

- **Порог значимости принадлежит батчу.** Null-world обязателен для каждого
  батча, а не «периодически»: порог зависит от числа проверенных гипотез.
  Замер внутри системы — от 2.60 при 10 кандидатах до 3.09 при 120.
- **Критерий заморожен вместе с формулой.** Хэш QUALIFICATION_POLICY входит
  в `strategy_hash`. Попытка смягчить критерий, увидев OOS, даёт HARD FAIL
  `CRITERION_CHANGED_AFTER_FREEZE`.
- **Просмотренный период не выдаёт ROBUST.** Даже при выполнении всех четырёх
  условий прогон на seen-данных помечается `REPLAY_OF_SEEN` и остаётся
  CANDIDATE. Это выполнение запрета документа 01 в коде, а не в инструкции.

Уровень `STRUCTURAL_MECHANISM` в пакете был объявлен без критерия. Здесь он
задан: чистый перенос без мутации формулы с вердиктом PASS минимум в двух
лигах помимо исходной. Сейчас недостижим — вторая лига не подключена.

## Что здесь принципиально

- **Утечка блокируется технически.** Любой признак до активации проходит
  `LeakageFirewall`: все зависимости обязаны иметь `kickoff < kickoff` целевого
  матча, а при неизвестном времени начала — принадлежать более раннему
  синхронному блоку (в сезонах 16-17…18-19 у Football-Data нет столбца `Time`).
- **NULL никогда не 0.** Недостаток истории даёт `UNAVAILABLE`, а не ноль.
- **Хронология по kickoff, не по туру.** Столбца тура в источнике нет.
- **Воспроизводимость привязана к окружению.** `dataset_version` и `result_hash`
  включают лок зависимостей; хэш считается от канонически округлённых значений,
  никогда от сырых float.
- **Holdout Ledger.** Система знает, сколько неоткрытых сезонов осталось в лиге,
  и отказывается запускать discovery, если батч обнуляет остаток.


## Исследовательская память (фаза 7)

`make memory` показывает, что лаборатория помнит.

Каждый батч начинается с обращения к памяти — это ключевой принцип документа 06,
и он выполняется кодом: `run_validation` не считает кандидата, про которого
память уже всё знает. На реальных данных из 120 кандидатов фазы 6 после прогона
фазы 7 к расчёту остаётся 6.

Три отпечатка отвечают на три разных вопроса:

| Отпечаток | Вопрос | Что входит |
|---|---|---|
| `exact` | это ровно тот же эксперимент? | формула + датасет + политики |
| `semantic` | такая логика вообще проверялась? | признак и направление, без чисел |
| `signal` | не то же ли это множество матчей? | список сработавших матчей |

Отсюда важное различие: **та же формула на новых данных — не дубликат,
а продолжение** (`RERUN_ON_NEW_DATA`), потому что `dataset_version` входит
только в exact.

Что ещё умеет память:

- **Исчерпанные области.** Если в участке пространства проверено достаточно
  порогов и ни один не прошёл порог батча, участок помечается исчерпанным —
  но только для этого датасета. На новых данных вопрос открыт заново.
- **PARK с условием возврата**, а не «когда-нибудь посмотрим»: сколько новых
  матчей должно появиться и до какой даты отложено.
- **KILL с кодом причины** из закрытого списка. Ничего не удаляется никогда.
- **Семейства по пересечению сигналов.** Две стратегии с Jaccard 0.945 — один
  механизм, а не два открытия.
- **Meta Memory**: сколько гипотез принёс признак, сколько прошло порог, лучший
  |z| за всю историю.
- **Решение машины и человека** хранятся раздельно и аудируются.
