## Р1. Хранилище: DuckDB + Parquet для аналитики, SQLite для состояния

ТЗ (п. 3) просит выбрать между DuckDB и PostgreSQL и обосновать.

**Выбор: DuckDB как движок запросов над Parquet-датасетами, SQLite для
транзакционного состояния приложения. PostgreSQL не нужен.**

Обоснование:

1. **Объём данных не требует сервера.** Топ-5 + вторые дивизионы за 10 сезонов —
   38 320 матчей, 76 640 строк витрины «команда-матч». При 200 признаках типа
   float32 это 61 МБ. Весь рабочий набор помещается в оперативную память
   целиком, и это меняет всю постановку задачи: узкое место не в вводе-выводе,
   а в арифметике перебора гипотез.
2. **DuckDB держит эксклюзивную блокировку файла на запись.** Если сложить в
   один `.duckdb` и загрузку данных, и майнинг, то бэкфилл заблокирует
   исследование. Поэтому слои `raw / core / features` живут в Parquet на диске,
   а DuckDB работает как движок запросов над ними (`read_parquet`) — читатели
   не блокируются, запись файла атомарна (temp + rename).
3. **Частые мелкие записи** (счётчики бюджета API, статусы задач, журнал
   форвард-теста) в колоночном хранилище противопоказаны. Для них SQLite в
   режиме WAL: конкурентное чтение и запись из коробки, ноль эксплуатации.
4. **Воспроизводимость.** Parquet-датасет с версией набора признаков в имени
   партиции позволяет пересобрать признаки заново и **побайтово сравнить** с
   предыдущей сборкой. Это техническая основа главного теста на утечку
   (см. [03-features.md](03-features.md), Т1).
5. **PostgreSQL оставлен как предусмотренный, но не стартовый вариант.** Если
   приложение станет многопользовательским или переедет на хост, слой
   `app.sqlite` переносится в Postgres через SQLAlchemy без единого изменения в
   аналитике. Аналитический слой в Postgres переносить не нужно и не стоит:
   полные сканы витрины там будут в 5–10 раз медленнее, а майнинг всё равно
   идёт в памяти.

Цена решения: два хранилища вместо одного. Она оправдана тем, что у них
принципиально разные профили нагрузки — большие редкие сканы против мелких
частых транзакций.

## Р3. Point-in-time как единственный способ построить признак

Запрет утечки (п. 1.4) — не проверка на выходе, а свойство слоя данных.

Каждый факт в `core` несёт колонку `known_at` (UTC) — момент, начиная с которого
факт мог быть известен:

| Факт | `known_at` |
|---|---|
| Счёт, статистика, события матча | `kickoff + 130 мин` |
| Стартовый состав | `kickoff − 60 мин` |
| Травма | дата публикации отчёта |
| Календарь, стадион, судья на матч | дата публикации назначения |

Витрина строится единственной функцией `build_team_match()`, и все агрегаты в
ней — оконные по строкам с `known_at < kickoff` целевого матча. Прямого доступа
к `core` из кода признаков нет: только через объект среза, который физически не
отдаёт строки из будущего.

Отдельно закрывается редкий, но реальный канал утечки: **границы бинов,
нормировки, коэффициенты сжатия к среднему и любые рейтинги силы команд
подбираются только на обучающем окне.** Квантили, посчитанные на всех данных,
протаскивают в обучение информацию о будущем распределении.

Каждый признак в реестре объявляет `availability_offset_min` — за сколько минут
до начала матча он становится известен. Стратегия объявляет горизонт решения
(`T−48ч` для планирования, `T−60мин` для ставок по составам). Валидатор
запрещает стратегии использовать признаки, недоступные на её горизонте.
Без этого признаки по составам молча превращают стратегию в невыполнимую.

Тесты на утечку описаны в [03-features.md](03-features.md).

## Р4. Майнинг на битовых масках

Так как весь набор помещается в память, кандидат представляется битовой маской
по матчам, а не выборкой строк.

- 38 320 матчей → 599 слов `uint64` на маску, 4.8 КБ.
- Атомарное условие («дней отдыха ≤ 3») → одна маска, считается один раз.
- Гипотеза = `AND` масок условий; число срабатываний = `popcount`.
- Исход рынка → две маски: `WIN` и `PUSH/HALF` (для форовых рынков).
- Одна гипотеза — примерно 0.6 мкс однопоточно.

| Гипотез | Время, 1 поток |
|---|---|
| 10⁵ | 0.2 с |
| 10⁶ | 1.8 с |
| 10⁷ | 18 с |
| 10⁸ | 3 мин |

Практическое следствие: **перестановочный тест перестаёт быть декоративным.**
1000 перестановок с полным повтором майнинга по 10⁶ гипотез — полчаса на одном
ядре, минуты на восьми. Именно поэтому в Р5 можно опереться на перестановки, а
не на грубую поправку.

Перебор идёт уровнями в стиле Apriori с отсечением по минимальной поддержке:
набор из трёх условий не может сработать чаще, чем любой его поднабор, поэтому
при пороге в 200 срабатываний (0.52% матчей) подавляющее большинство ветвей
отсекается на глубине 2. Без отсечения глубина 3 — это 4·10⁹ гипотез, с ним —
порядка 10⁵–10⁷. Счётчик реально проверенных гипотез ведётся точно, он же идёт
в поправку на множественность.

## Р5. Множественность: перестановочный max-статистик, БХ поверх него

ТЗ (п. 8) требует и процедуру Бенджамини–Хохберга, и перестановочный тест.
Взятая буквально, БХ по числу гипотез автомайнинга не оставляет ничего:

| Проверено гипотез | Порог p для первой находки при FDR 10% |
|---|---|
| 10³ | 1·10⁻⁴ |
| 10⁵ | 1·10⁻⁶ |
| 10⁷ | 1·10⁻⁸ |

Достижимый односторонний биномиальный p при базе 0.50: `n=200, p̂=0.60` даёт
2.8·10⁻³, `n=500, p̂=0.60` даёт 4.5·10⁻⁶. То есть при реалистичном размере
эффекта и реалистичной выборке БХ по 10⁷ гипотез не пропустит ничего, и
приложение окажется пустым — после чего возникнет соблазн ослабить порог, что
и есть тот самый провальный сценарий из преамбулы ТЗ.

Причина не в консервативности БХ, а в допущении независимости: перекрывающиеся
стратегии (одна и та же находка с чуть сдвинутым порогом) считаются
независимыми проверками, хотя это одна проверка.

**Предложение — связать оба требования ТЗ в одну процедуру:**

1. Перемешиваем исход внутри блоков (лига × сезон), сохраняя базовые частоты.
2. Полностью повторяем майнинг на перемешанных данных.
3. Записываем **максимум** статистики по всему перебору — это распределение
   «лучшая находка на чистом шуме» из п. 8.
4. Эмпирический p-value стратегии = доля перестановок, где максимум оказался не
   хуже её статистики. Это контроль FWER, учитывающий корреляцию гипотез
   (Westfall–Young step-down; в приложении к перебору торговых правил —
   White's Reality Check и Hansen SPA).
5. БХ применяется к этим перестановочным p-value для контроля FDR при отборе
   нескольких стратегий.

Требования ТЗ выполняются оба, но БХ работает по корректным p-value, а не по
номинальным.

## Р6. Обобщённая формула коэффициента безубыточности

Разобрано в [04-markets.md](04-markets.md). Кратко: `К_бе = 1 + B/A`, где
`A = p_win + p_half_win/2`, `B = p_loss + p_half_loss/2`. Для бинарного рынка
сводится к `1/p̂` из п. 1.2 ТЗ; для азиатских четвертных фор и рынков с возвратом
даёт корректный ответ там, где `1/p̂` неопределено.

## Р7. Порядок этапов: бэкфилл выносится в фон

Полный бэкфилл — это 7–15 суток календарного времени при лимите 7500
запросов/сутки (расчёт в [06-roadmap.md](06-roadmap.md)). В ТЗ это этап 3 с
пометкой «усилие обычное», и по объёму работы разработчика это верно, но по
календарю он блокирует всё остальное.

Данные football-data.co.uk дают за 10 сезонов результаты, счёт по таймам, удары,
удары в створ, угловые, фолы, карточки и судью — этого хватает для этапов 4–6
целиком. **Рекомендация: бэкфилл запускается фоновым демоном сразу после этапа 2
и идёт параллельно разработке этапов 4–8.** Экономит одну-две недели.
