## Главная правка порядка: этап 3 не блокирует ничего

В ТЗ бэкфилл стоит третьим и по смыслу предшествует работе с признаками. По
объёму работы разработчика оценка «обычное усилие» верна — это цикл с
очередью. Но по календарю это не день и не два.

### Расчёт бюджета

Лимит 7500 запросов в сутки, жёсткая остановка на 90% (п. 2 ТЗ) — фактически
6750 в сутки.

Скелет календаря стоит почти ничего: `/fixtures?league&season` — один запрос на
лигу-сезон, около 100 запросов на весь проект. Дорого стоит поматчевая
детализация: `statistics`, `events`, `lineups` — по одному запросу на матч.

| Охват | Что тянем | Запросов | Суток при 90% стопе |
|---|---|---|---|
| Топ-5, 10 сезонов (17 520 матчей) | statistics + events + lineups | 52 660 | 7.8 |
| Топ-5, 10 сезонов | events + lineups, статистика из CSV | 35 140 | 5.2 |
| Топ-5, 10 сезонов | только events | 17 620 | 2.6 |
| Топ-5 + вторые, 10 сезонов (38 320 матчей) | statistics + events + lineups | 115 060 | 17.0 |
| Топ-5 + вторые | events + lineups, статистика из CSV | 76 740 | 11.4 |
| Топ-5 + вторые | только events | 38 420 | 5.7 |

### Что из этого следует

1. **Разработка идёт на данных CSV, а не ждёт API.** football-data.co.uk
   покрывает ровно нужные дивизионы (`E0 E1 SP1 SP2 I1 I2 D1 D2 F1 F2`) и даёт
   за все десять сезонов: результат, счёт по таймам, удары, удары в створ,
   угловые, фолы, карточки, судью. Этого хватает для всей первой очереди
   признаков ([03-features.md](03-features.md)) и, соответственно, для этапов
   4, 5 и 6 целиком.
2. **Скелет календаря тянем сразу** — 100 запросов дают точное время начала
   матчей, стабильные `team_id`, стадион и статус. Заодно это решает задачу
   маппинга названий из CSV на идентификаторы API: сопоставление идёт по дате,
   счёту и приблизительному названию, а не по одному названию.
3. **Приоритет поматчевых запросов:** сначала `events` (голы с минутами —
   нужны для 15-минутных интервалов и второй очереди признаков), затем
   `statistics` для лиг, где CSV не покрывает, и только потом `lineups`.
   Составы имеют смысл лишь на горизонте `T−60 мин` (С9), поэтому для истории
   они наименее ценны.
4. **Приоритетная очередь по п. 2 ТЗ:** матчи ближайших дней всегда впереди
   добора истории. Форвард-тест не должен простаивать из-за бэкфилла.

### Рекомендация по стартовому охвату

Начать с топ-5 (7.8 суток), вторые дивизионы добирать вторым заходом. Причина
не только в бюджете: вторые дивизионы дают вдвое больше матчей и потому вдвое
больше кандидатов при переборе, а значит и более жёсткую поправку на
множественность. Разумнее сначала убедиться, что вся цепочка работает на топ-5.

## Этап 1 — что конкретно делается

Механическая реализация по готовой спецификации, проектных решений не требует
(п. 13 ТЗ), при условии что решения Р1–Р4 согласованы.

```
apps/lab-api/
├── lab/
│   ├── config.py          настройки из переменных окружения
│   ├── storage/           duckdb.py, parquet.py, sqlite.py, migrations/
│   ├── models/            pydantic-схемы core и features
│   ├── api/               роутеры FastAPI
│   └── cli.py             lab backfill / lab features build / lab mine
├── tests/
│   ├── test_storage.py
│   └── conftest.py
└── pyproject.toml
apps/lab-web/              vite + react + ts + tailwind, тёмная тема, каркас экранов
docker-compose.yml         api, worker, web, общий том ./data
```

Критерий готовности этапа 1: `docker compose up` поднимает три сервиса,
`GET /health` отвечает, создаются пустые Parquet-датасеты и `app.sqlite` со всеми
таблицами, тесты проходят, фронтенд открывается с пустым дашбордом на тёмной
теме.

## Отчётность по п. 13

В начале каждого этапа — одна фраза о том, требует ли он проектных решений.
Немедленный сигнал при любом из четырёх событий:

- две неудачные попытки подряд починить одно и то же;
- код запустился, но результат выглядит подозрительно хорошо;
- надо выбрать между вариантами, а не реализовать заданное;
- спецификация противоречит сама себе или не покрывает случай.

Второй пункт для этого проекта — главный. Стратегия с точностью 70% на выборке
из 300 матчей после всех проверок скорее означает ошибку в коде расчёта исхода
или утечку, чем находку. Порядок действий при таком результате: сначала
проверить `settle()` и тесты на утечку, потом радоваться.

После каждого этапа — короткий отчёт: что сделано, что проверено, где риски,
что осталось незакрытым.
